# Botfood: нативный Nginx-модуль для обманной медленной выдачи ботам

**Статус:** техническая спецификация идеи для реализации агентом. **Язык реализации:** C (базовый путь); Rust/Zig — возможны после проверки ABI и интеграции с фазами Nginx.

## 1. Задача

Публичные веб-приложения регулярно получают массовые автоматические запросы к путям вида `/.env`, `/.git/HEAD`, `/user_secrets.yml`, резервным копиям и другим типовым объектам сканирования. Обычный `404` позволяет сканеру мгновенно двигаться дальше. Botfood должен дешёво перехватывать **известные модулю подозрительные URL**, отдавать на них убедительный синтетический контент с `200 OK` и **передавать тело очень медленно**, удерживая запрос настолько долго, насколько это позволяет клиент и промежуточные прокси. Неизвестные модулю URL должны без заметных побочных эффектов продолжать обычный путь обработки Nginx.

Это **не** универсальная замена маршрутизации, WAF и rate limiter и **не** подмена всех `404`. Начать с точного распознавания известных подозрительных путей; лабиринты, динамическое порождение новых URL и федерация телеметрии — возможные будущие расширения.

### Цели

- Включение одним флагом на уровне `http` или `server` без ручного перечисления ловушек в `location`.
- Встроенная расширяемая база подозрительных URL/паттернов. **Белый список необязателен и по умолчанию не включён.** Возможность подключить пользовательские исключения и дополнительные сигнатуры.
- Совпадение: синтетический `200 OK` и медленная неблокирующая потоковая выдача правдоподобного контента. Ни запрос, ни его тело не передаются реальному приложению.
- Отсутствие совпадения: вернуть `NGX_DECLINED`, продолжить обычные фазы и штатный поиск `location` в Nginx. **Не** выполнять второй HTTP-запрос, `proxy_pass`, внутренний редирект или маркировку заголовком для повторного прохода.
- При исчерпании лимита одновременных медленных ловушек: сразу ответить `200 OK` короткой приманкой и завершить ответ. Не допускать очередей и не возвращать `503`.
- Очень низкая цена на CPU/память/исходящий трафик; отсутствие внешнего сервиса и базы данных.
- Измеримые фактическая продолжительность удержания, тайм-ауты/разрывы клиента и расход ресурсов.

### Не-цели

- Выявление всех вредоносных клиентов по IP, User-Agent, поведению или ML.
- Бесконечная выдача гигабайтов, принудительное удержание клиента после его тайм-аута, открытие исходящих соединений к атакующему.
- Реалистичный интерактивный фальшивый API/репозиторий с бесконечным графом ссылок (возможная v0.2).
- Центральная координация между несколькими хостами, Redis/Valkey/другая memory DB.
- Перехват всего, что вернуло бы `404`.

## 2. Конвейер запросов

```text
client → Nginx request
       → Botfood handler (до штатного location lookup)
          ├─ URI не совпал ───────→ NGX_DECLINED → обычная маршрутизация Nginx
          └─ URI совпал
             ├─ slow-slot доступен → 200 OK → таймеры и малая порционная выдача
             │                                 → cleanup → освободить слот
             └─ slow-slot занят   → 200 OK → небольшой фрагмент той же приманки
                                            → закончить ответ
```

Рекомендуемая точка интеграции: обработчик `NGX_HTTP_SERVER_REWRITE_PHASE`, исполняемый до `NGX_HTTP_FIND_CONFIG_PHASE`, чтобы известные пути отсеивались независимо от `location`; проверить порядок фаз, наследование настроек `http`/`server`, влияние пользовательских rewrite-правил и внутренние редиректы на целевой версии Nginx. Если конкретная сборка или конфигурация препятствует такому порядку, явно задокументировать ограничение. Обработчик должен предотвращать повторный вход для уже обработанного запроса. Вариант установки в `PREACCESS` не заменяет глобального перехвата **до** поиска `location`; не переносить туда без пересмотра требований.

**Примечание о заголовке:** исходная идея «вернуть запрос в Nginx с заголовком» реализуется дешевле и точнее через `NGX_DECLINED`. Не добавлять исходящему клиенту или upstream фиктивный заголовок при обычном пропуске. Дополнительный диагностический заголовок только в явно включённом debug-режиме.

## 3. Распознавание подозрительных URL

Встроенный набор правил, версионируемый и проверяемый тестами. Приоритет — высокая точность, поскольку по совпавшему пути вместо настоящего обработчика отработает ловушка. Примеры категорий:

- Файлы окружения/секретов: `/.env`, варианты `.env.*` с чётко определёнными масками, `/user_secrets.yml`, `config/*.yml` только для конкретных известных рискованных путей.
- Git и метаданные: `/.git/HEAD`, `/.git/config`, `/.svn/entries`.
- Известные имена дампов и бэкапов (`*.sql`, `*.bak`, `backup.zip`) **только если маска достаточно конкретна**; не перехватывать всякий `.sql`/`.zip` без дополнительных условий.
- Явно опознанные пути автоматического поиска админок/типовых приложений, но с учётом того, что `/admin`, `/docs`, `/openapi.json`, `/robots.txt` и т.п. вполне могут быть легитимными на настоящем сайте. **Не добавлять эти неоднозначные пути в дефолтный набор без решения владельца.**

Обрабатывать path отдельно от query string; решить и тестировать политику percent-decoding, двойного encoding, повторных слешей, `.`/`..`, регистра и UTF-8. Использовать нормализованное Nginx URI (`r->uri`) и, если требуется, исходный URI только для диагностики; не допустить обхода правил через различия нормализации. `HEAD` возвращает заголовки без тела и не удерживает слот как длительную выдачу; другие методы — явно определить политику, по умолчанию не ловить небезопасные методы и пропускать их дальше, если это не создаёт отдельную угрозу приложению. Не считывать и не буферизовать тело неизвестного запроса.

Порядок правил: явные пользовательские исключения → встроенные + пользовательские сигнатуры → пропуск. Исключения не требуются для работы, но нужны для сайтов, на которых подозрительное имя файла является настоящим ресурсом. Учитывать `server_name`/наследование конфигурации при использовании в нескольких vhost.

## 4. Синтетический ответ

Для совпавшего паттерна выбирать соответствующий тип приманки: `.env` → строки `KEY=VALUE`; `.git/HEAD` → `ref: refs/heads/main`; `.git/config` → правдоподобный фиктивный git config; `user_secrets.yml` → синтетический YAML; backup → маленькая имитация содержимого, а не настоящий архив, если формат нельзя корректно сгенерировать в рамках бюджета.

- **Никаких настоящих секретов, IP-адресов, доменов третьих лиц или рабочих credentials**; использовать заведомо фиктивные значения и зарезервированные домены (`.invalid`, `example.com`) там, где это уместно. Синтетические адреса не должны вести к реальным сторонним системам.
- Содержимое по возможности детерминировано по seed с согласованными идентификаторами, чтобы повторные запросы получали правдоподобные данные без БД. Допустимы предсозданные шаблоны; не запускать LLM на запрос.
- Начальный быстрый фрагмент должен выглядеть содержательно: сервер отправляет заголовки `200 OK` и начало файла, затем выдаёт небольшие фрагменты по таймеру. Размер и частота настраиваются, можно добавить jitter.
- Не устанавливать `Content-Length`, несовместимый с фактически переданным телом; при потоковой передаче использовать корректное framing для HTTP/1.1 и HTTP/2. Настроить `Content-Type` под файл. Рассмотреть `Cache-Control: no-store`, отключить сжатие/буферизацию там, где они разрушают медленный профиль. Промежуточные CDN и reverse proxy могут переупаковывать или обрывать поток: это ограничение, которое необходимо тестировать.
- Корректно завершать ответ по достижении лимита продолжительности/размера или при отключении клиента. Не пытаться бесконечно генерировать тело.

## 5. Медленная неблокирующая выдача

Без `sleep()`, отдельных потоков на соединение и busy loop. Подключить write/event handler и `ngx_add_timer` к штатному event loop. Хранить компактный request-local context: выбранный шаблон, seed, смещение, время старта, отправленные байты, состояние таймера и признак владения slow-slot. Таймер → сформировать следующий фрагмент → неблокирующая передача → снова запланировать таймер. Учитывать частичную запись, backpressure, `NGX_AGAIN`, отмену таймеров и request lifetime в соответствии с Nginx API. Не блокировать worker, если клиент перестал читать.

Начальные параметры для эксперимента, **не зафиксированные продуктовые значения**:

| Параметр | Экспериментальный старт |
|---|---:|
| Размер фрагмента | 64–256 Б |
| Интервал | 2–10 с |
| Максимальная длительность | 10–60 мин |
| Максимальный размер ответа | 16–64 КБ |
| Медленных слотов | 1000 (настраивается) |

Ни длительность, ни медленная передача не гарантируют фактическое удержание: клиент и reverse proxy могут разорвать соединение раньше. Измерять фактический результат, не выдавать заданную длительность за реальную.

## 6. Учёт slow-slot и перегрузка

Один счётчик одновременно исполняемых **медленных** ловушек в Nginx shared memory (`ngx_shm_zone_t` / атомарный тип Nginx), общий для worker-процессов. Никаких Redis и сетевых обращений. Один атомарный `fetch_add` при захвате и `fetch_sub` при освобождении — либо иной корректный механизм с теми же свойствами. По возвращённому прежнему значению определить, получен ли слот; если прежнее значение >= лимита, немедленно вернуть инкремент и выдать короткую приманку. Это устраняет массовый oversubscription без CAS, допускается несущественная кратковременная погрешность метрик. Не применять сначала неатомарную проверку, а потом отдельный инкремент.

Освобождать слот **ровно один раз** через единый cleanup path при завершении, отмене, клиентском disconnect и ошибке. При аварийном завершении worker shared counter может остаться завышенным; предусмотреть дешёвый сценарий восстановления (например, поколение worker и учёт на worker / восстановление при reload). Для MVP явно задокументировать ограничение, дать диагностическую команду/метрику; не обнулять общий счётчик на живом reload, пока старые workers обслуживают запросы.

Если лимит достигнут:

1. Немедленно вернуть `200 OK`.
2. Отправить **короткий** синтетический фрагмент, соответствующий распознанному пути.
3. Корректно завершить HTTP-ответ, без длинного таймера, ожиданий и очереди.

Сохранить стандартные защитные лимиты Nginx как последний барьер. Не завязывать дизайн на преждевременную оптимизацию десятков/сотен тысяч соединений: в приведённом примере ожидается порядок до тысяч подозрительных запросов в час, не DDoS.

## 7. Конфигурация: проект публичного API

Имена директив ниже **предлагаемые**, их нужно реализовать и проверить. Включение на уровне `http` и по возможности переопределение на уровне `server`:

```nginx
load_module modules/ngx_http_botfood_module.so;

http {
    botfood on;

    # Встроенные сигнатуры включены по умолчанию при botfood on.
    # Оба файла полностью опциональны:
    # botfood_allowlist /etc/nginx/botfood/allowlist.conf;
    # botfood_patterns /etc/nginx/botfood/extra-patterns.conf;

    botfood_max_slow 1000;
    botfood_chunk_size 128;
    botfood_chunk_interval 5s;
    botfood_max_duration 30m;
    botfood_max_body 32k;

    server {
        listen 443 ssl;
        server_name example.com;
        # Остальная конфигурация сайта не меняется.
    }
}
```

Выключенный модуль не должен вмешиваться ни в один запрос. После включения **не нужно** перечислять `location` для ловушек. Добавить `botfood off` в конкретном server при необходимости. Базовые пресеты `gentle`, `slow`, `aggressive` возможны позже; не перегружать ими MVP.

Если выбран не C, а Rust/Zig, сначала написать минимальный динамический модуль, который проходит `nginx -t`, корректно попадает в нужную фазу и возвращает `NGX_DECLINED`, а уже потом реализовывать сложную потоковую логику. Не предполагать, что любой экспериментальный Rust SDK поддерживает все нужные низкоуровневые API без FFI.

## 8. Логи и метрики

Не засорять основной access log отдельными событиями каждого фрагмента. На завершённый запрос — одна структурированная запись по настраиваемому уровню. Метрики:

- число совпадений по сигнатуре и vhost;
- число медленных ловушек и мгновенных fallback;
- текущие/пиковые slow-slot;
- фактическая длительность соединения/запроса, медиана и распределение;
- причина завершения: завершена выдача, timeout, disconnect, send error, shutdown;
- отправленные байты и число фрагментов;
- оценочная стоимость CPU/памяти и влияние на latency обычных запросов.

При нахождении за Docker/reverse proxy внутренний адрес наподобие `172.18.0.5` может быть адресом прокси, а не бота. IP в журнале брать только из стандартной проверенной конфигурации Nginx Real IP для **доверенных** прокси, не доверять произвольному `X-Forwarded-For` из интернета. Не сохранять реальные query strings/секреты в telemetry без необходимости.

## 9. Тесты и критерии приёмки

### Функциональные

1. На `/.env`, `/.git/HEAD`, `/user_secrets.yml` выдаётся синтетический `200 OK` соответствующего формата; тело передаётся порциями, запрос не достигает upstream.
2. Обычный `/`, `/api/...` и любые URL вне базы попадают в стандартную маршрутизацию без повторного HTTP-запроса и дополнительных заголовков.
3. Явный allowlist исключает совпавший URL из ловушки, но его отсутствие не мешает старту модуля.
4. Добавленная пользовательская сигнатура работает после reload; конфигурационные ошибки выявляются командой `nginx -t`.
5. При заполненном лимите модуль выдаёт короткий синтетический `200 OK` и завершает ответ без удержания.
6. `HEAD`, percent-encoding, повторные слеши, `internal redirect`, разные vhost и запросы с query string покрыты отдельными тестами.

### Системные

7. При разрыве соединения клиентом, ошибке записи и окончании таймера слот возвращается ровно один раз.
8. `nginx -s reload` со старыми активными медленными запросами не обнуляет состояние преждевременно и не приводит к двойному освобождению.
9. HTTP/1.1 и HTTP/2 работают корректно; нет некорректного `Content-Length` и преждевременного закрытия чужих HTTP/2 stream.
10. Медленный клиент не блокирует worker и не повышает латентность обычных запросов сверх заранее заданного порога.
11. Если соединение рвёт прокси/CDN, это регистрируется как фактический исход; длительность не приукрашивается.
12. Под нагрузкой в несколько тысяч обнаружений в час сохраняются стабильная память и число дескрипторов; fallback предсказуем при искусственно малом лимите.

## 10. Порядок реализации агентом

**Этап A — каркас:** выбрать поддерживаемую версию Nginx; создать собираемый динамический C-модуль; директива `botfood on`; обработчик в фазе до `location`, логирование совпадений; `NGX_DECLINED` для прочих. Автоматические интеграционные тесты в Docker.

**Этап B — приманки:** встроенные точные пути и расширяемый matcher, генераторы `.env`, YAML, Git metadata. Простой немедленный `200` на совпадение. Проверить, что upstream не затрагивается.

**Этап C — tarpit:** request context + неблокирующие таймеры + порционная выдача с корректным HTTP-framing, cleanup на disconnect/error/complete. Измерять реальное удержание.

**Этап D — shared counter:** лимит slow-slot, атомарный учёт, немедленный короткий fallback; тесты при конкурентных запросах, reload и обрыве worker.

**Этап E — релиз:** allowlist, custom patterns, логирование/метрики, README с примерами конфигурации и предупреждениями о CDN, CI под заявленные версии Nginx, нагрузочные тесты и лицензия опенсорсного проекта.

**Отдельное решение перед реализацией:** определить, нужно ли вообще ловить потенциально легитимные `/docs` и `/openapi.json`. По умолчанию **нет**: в приведённом логе это реальные `200 OK` приложения, и перехватывать их без явного разрешения значит ломать API-документацию. Их можно включить пользовательскими правилами там, где они точно не нужны.

## 11. Дальнейшие идеи (не блокируют)

- Лабиринт: согласованный синтетический OpenAPI, взаимосвязанные фальшивые URL и seed-based fake repository.
- Отдельные профили выдачи по категории пути и эксперимент с интервалами, размером фрагмента, jitter.
- Проверка того, какие классы сканеров действительно ждут медленные ответы, с анонимизированными агрегированными метриками.
- Обновляемый подписанный каталог сигнатур без обновления бинарника; без передачи наружу исходных логов сайта.
- Межсерверная координация только если появится конкретная необходимость.

## 12. Принципы проекта

**Не блокировать обычный трафик. Не создавать дорогостоящую инфраструктуру ради одного счётчика. Не делать медленную ловушку дороже для сервера, чем для клиента.** Подозрительный известный URL → убедительный синтетический `200 OK` и медленная передача; всё остальное → штатный Nginx. При перегрузке → короткий `200 OK` и освобождение ресурсов.
